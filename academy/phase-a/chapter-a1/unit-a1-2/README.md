# A1.2｜从业务需求到评测问题

> 本单元训练一种关键能力：把含混的业务愿望转换为有对象、有边界、有风险、有构念、有证据要求、能够触发具体动作的评测问题。评测设计的核心不是先挑指标，而是证明某个版本的系统在声明条件下是否足以支持一个明确决定。

[独立 HTML 阅读版](index.html) · [Academy 首页](../../../README.md) · [工程资产清单](artifact-manifest.yaml)

## 1. 学习目标

完成本单元后，应当能够：

1. 从业务愿望中分离产品目标、实现方案、KPI、约束与待批准决定。
2. 明确 Intended Use、Prohibited Use、Evaluation Target 和结论边界。
3. 建立 stakeholder-impact mapping，识别直接用户之外的数据主体、责任人和受影响资产。
4. 用统一 taxonomy 编写可验证、可分级、可处置的风险陈述。
5. 将“准确、安全、可靠、专业”等抽象词操作化为 construct、正反例和边界例。
6. 将构念转换为 Evaluation Question 和 Evidence Requirement，并建立双向追踪。
7. 识别代理指标失效、对象漂移、场景遗漏和不可验证需求。

## 2. 从愿望到证据的主链

真实需求通常混合了愿望、方案和口号，例如：“下月全员上线”“使用更强模型加 RAG”“准确率达到 90 分”“绝对不能幻觉”。这些句子不能直接成为上线证据。

应按以下顺序转换：

```text
业务愿望
→ 产品目标与责任边界
→ 待批准决定
→ Intended / Prohibited Use
→ Stakeholder-impact mapping
→ Risk taxonomy 与风险陈述
→ Construct operationalization
→ Evaluation Questions
→ Evidence Requirements
→ Requirements-to-evidence traceability
→ Pass / Fail / Inconclusive / Conditional Pass
```

这条链同时支持两种审查：从每项重要业务风险向前寻找证据与动作；从每项指标向后寻找它代表的构念和支持的决定。

### 2.1 五类核心资产如何分工

这五类资产不是五份彼此独立的表格，而是一条逐步收窄结论的控制链：

| 资产 | 它回答的问题 | 它把什么传给下一步 |
|---|---|---|
| Evaluation Charter | 谁要在什么时候决定什么？允许与禁止的用途是什么？ | 决策、Target、范围、结果类型与关键限制 |
| Stakeholder-impact mapping | 系统行为会通过什么路径影响谁、什么权益或资产？ | 影响链、责任人、控制与待证明的伤害路径 |
| Risk taxonomy | 哪些失败值得独立管理，如何统一描述严重性与容忍度？ | 可验证的风险陈述与不可补偿规则 |
| Construct operationalization | “可靠、安全、专业”在本场景具体是什么意思？ | 正反边界例、观察、参考标准与效度限制 |
| Evidence Requirement | 什么数据、场景、观察和评分质量才足以回答问题？ | 可审计的证据包、充分性规则与证据不足动作 |

它们之间存在反馈，而不是单向流水线。例如 stakeholder mapping 新发现“未直接使用系统的数据主体”，Charter 的禁止用途和风险清单就必须回写；构念无法被可靠观察时，不能降低定义迁就现有数据，而应修改 Evidence Requirement、补建观测，或把结论标成 `Inconclusive`；证据显示两个子范围不能被可靠隔离时，Charter 也不能继续保留 `Conditional Pass` 选项。

### 2.2 同一句模糊需求，为什么产生三套评测设计

假设三个团队都只说一句：**“这个 Agent 要可靠，可以上线。”** 这句话的价值方向相同，但系统改变世界的方式不同，所以不能共用一套“可靠性准确率”。

| 推导环节 | 退款 Agent | 合同审查 Agent | 企业知识助手 |
|---|---|---|---|
| 待批准决定 | 是否允许在金额、地区、政策范围内自动写入退款 | 是否允许对声明合同类型做律师复核前的首轮筛查 | 是否允许员工在批准知识域获得带证据信息回答 |
| 核心受影响方 | 消费者、商户、财务与客服 | 律师、业务签约方、合同相关数据主体 | 员工、个人数据主体、HR/IT 与文档所有者 |
| 关键风险 | 未授权退款、重复写账、漏升级 | 高严重性条款漏检、伪造原文、越过律师责任 | 无依据或过期制度、ACL 泄露、把说明变成正式决定 |
| 关键构念 | 政策合规、状态安全、适当升级 | 关键风险召回、原文定位、校准升级 | 可回答性、有据性、新鲜度、访问隔离、适当拒答 |
| 必需场景 | 超时、重试、并发、审批失效、金额边界 | 跨条款、附件缺失、司法辖区、专家分歧、困难负例 | 多身份同问、新旧制度、无答案、来源冲突、提示注入 |
| 决定性证据 | 工具轨迹、审批记录、幂等键、账本最终差异 | 专家金标、风险类别、字符级原文 span、候选负担 | 文档版本与 ACL、检索上下文、原子主张—证据 span、全路径日志 |
| 不能替代的代理指标 | 最终回复“退款成功”的文本正确率 | 总体风险标签准确率或“像律师”的 Judge 分 | 引用率、FAQ 正确率或咨询量下降 |

因此，模糊需求不是直接“翻译”为指标，而要经过决定、影响、风险、构念和证据五次收窄。同一句话最后可能分别需要一个状态化 Sandbox、一套专家合同金标、以及一个多身份版本化知识环境；这正是从业务需求到评测问题的核心能力。

### 2.3 五种句子必须严格分开

| 层次 | 定义与规范句式 | 知识助手示例 | 不能冒充它的内容 |
|---|---|---|---|
| 业务愿望 | 组织希望发生的价值方向，常写成“我们希望……” | 希望员工更快获得制度信息并减少重复咨询 | 不是可证伪命题，也不是上线门禁 |
| 产品目标 | 产品直接输出如何改善用户结果与业务结果，并受什么 guardrail 约束 | 提供当前制度的自助信息回答，使员工更快找到流程；不得泄露受限信息 | “使用 RAG”是方案；“咨询量减半”单独只是 KPI |
| 风险陈述 | 在触发条件下，经由失败机制影响某方并造成伤害；同时声明严重性、容忍度、观察与动作 | 普通员工查询通用制度时，受限文档进入上下文，导致个人信息泄露；一经确认即阻断该范围 | “存在安全风险”没有机制、受影响方和处置 |
| 决策问题 | 某个责任人依据证据，在候选动作中选择什么 | 产品负责人是否允许正式员工在两个批准知识域使用候选版本，还是阻断、补证或只开放子范围？ | “准确率是多少”没有责任人和候选动作 |
| 评测问题 | 针对声明 Target、总体和场景，对某个已定义构念提出可由证据回答的经验问题 | 不同身份询问相同问题时，检索、上下文、回答、错误信息与日志是否始终满足访问隔离？ | “让 Judge 打分”是评分方法，不是问题本身 |

五者的方向也不同：业务愿望和产品目标说明**为什么值得做**；风险陈述说明**什么不能接受**；决策问题说明**证据将改变什么动作**；评测问题说明**具体要观察什么才能回答决定**。指标只在这五层之后出现，它是证据的摘要方式，不是其中任何一层的替代品。

## 3. 第一步：重写决定，而不是重写口号

一个可评测的决策问题至少包含：责任人、候选动作、系统版本、用户、用途、权限、场景、截止条件和失败后的动作。

| 含混表达 | 可决策表达 |
|---|---|
| 退款 Agent 能不能上线？ | 是否允许候选版本在声明地区、金额上限和政策范围内自动执行退款，其余请求必须升级？ |
| 合同 Agent 是否达到律师水平？ | 是否允许系统对声明合同类型执行首轮筛查，并把带原文定位的风险候选交给律师复核？ |
| 知识助手能否全员使用？ | 是否允许正式员工在已批准知识域中获取基于当前授权文档的带引用信息回答？ |

决策对象必须与实际运行对象和报告结论一致。评测裸模型不能证明完整产品可上线；评测文本答案不能证明 Agent 的工具调用和环境状态安全。

## 4. 第二步：锁定用途、对象与边界

### 4.1 Intended Use

至少声明：谁使用、解决什么任务、在哪些知识域或业务流程、允许产生什么输出、如何进入后续工作流。

### 4.2 Prohibited Use

明确系统不得处理的身份、数据、领域、动作和责任。例如信息助手不得作正式审批，合同筛查不得替代律师签署意见，退款 Agent 不得在状态未知时重复写账。

### 4.3 Evaluation Target

沿完整链路列出版本与组件：身份、权限、检索、模型、提示词、工具、编排、环境状态、日志和人工接管。结论只能覆盖实际被测的对象与配置。

## 5. 第三步：Stakeholder-impact mapping

利益相关方不只包括点击按钮的人。至少检查：

| 角色 | 可能获得的价值 | 可能承受的伤害 | 所需控制 |
|---|---|---|---|
| 直接用户 | 更快完成任务 | 被错误结论误导 | 有据性、拒答、纠错入口 |
| 决策对象或数据主体 | 更一致的处理 | 权益、隐私或声誉受损 | 权限隔离、人工复核、申诉 |
| 业务与资产负责人 | 降低重复工作 | 财务、法律或运营损失 | 硬门禁、审计、回滚 |
| 系统运营者 | 更高自动化 | 告警疲劳、责任不清 | 责任人、处置时限、运行手册 |
| 治理角色 | 可审计的控制 | 证据不足或错误归因 | 证据保留、独立复核、例外审批 |

映射必须把“谁受到什么影响”连接到风险、构念和证据，不能只列一份联系人名单。

## 6. 第四步：Risk taxonomy 与风险陈述

统一 taxonomy 可避免只测试容易量化的功能正确性：

| 风险域 | 典型问题 |
|---|---|
| 任务与事实 | 错答、漏答、无依据主张、引用误导 |
| 权限与隐私 | 越权读取、敏感信息推断、日志泄露 |
| 行动与状态 | 错误工具、重复副作用、状态未知仍执行 |
| 人机责任 | 不当自动决定、漏升级、人工控制无效 |
| 公平与权益 | 特定群体系统性受损、缺少申诉 |
| 鲁棒与安全 | 提示注入、污染输入、依赖异常 |
| 运营与经济 | 延迟、成本、可用性、恢复失败 |
| 治理与证据 | 版本不明、证据不可复现、责任不清 |

一条完整风险陈述应回答：在什么触发条件下，系统通过什么失败机制，影响谁或什么资产，造成何种伤害；严重性和容忍度如何；用什么观察判定；失败后谁做什么。

关键风险通常不可补偿。一次确认的权限泄露或未经授权的资金状态变化，不能被大量普通样本的高平均分抵消。

## 7. 第五步：Construct operationalization

构念是想测但不能直接观察的属性。操作化不是给抽象词换一个英文名，而是固定其含义和判定边界。

每个构念至少包含：

- 定义及与相邻构念的区别；
- 正例、反例和边界例；
- 分析单位与适用总体；
- 可观察信号和参考标准；
- 候选评分方式及评分器限制；
- 不能由该构念推出的结论。

例如“有据性”不是“存在引用”。它要求回答中的关键原子主张被系统实际获得、当前有效且用户有权访问的证据所支持；引用数量只能是诊断信号，不能单独作为门禁。

## 8. 第六步：形成 Evaluation Question

好的评测问题通常采用以下结构：

> 对于【声明总体与场景】，被测系统是否能够【满足某构念】，依据【参考标准与可观察证据】判定；结果将支持【哪项决定或动作】？

评测问题应避免：

- “系统是否足够智能”这类无限对象；
- “准确率是多少”这类没有用途和风险的指标提问；
- 把评分方法写成问题，例如“让 Judge 打几分”；
- 把当前不可观察的状态伪装成可验证结论。

## 9. 第七步：定义 Evidence Requirement

证据要求要先于数据集制作和评分脚本。至少声明：

1. **来源与代表性**：真实流量、专家构造、风险枚举各承担什么用途。
2. **场景矩阵**：常规、边界、异常、高风险低频、身份、时间和对抗场景。
3. **参考标准**：谁有资格给出真值，如何处理分歧、版本与不确定性。
4. **观察范围**：答案、引用、检索、轨迹、工具调用、权限和最终环境状态。
5. **评分可靠性**：规则、人工或 Judge 的校准、盲审、仲裁及误差。
6. **独立性与版本**：受保护门禁集、污染控制、目标版本和运行配置。
7. **充分性**：样本、重复运行、切片和不确定性是否足以支持所声明决定。
8. **保留与审计**：证据 ID、哈希、时间、责任人和重放能力。

流量代表性与风险覆盖不能互相替代。低频高伤害事件在随机样本中可能完全缺席，必须主动构造和故障注入。

## 10. 需求到证据追踪

追踪矩阵应至少连接：

```text
原始需求 → 决策 → 利益相关方 → 风险 → 构念
        → 评测问题 → 场景 → 证据 → 门禁规则 → 责任人与动作
```

状态建议使用 `covered`、`partial`、`blocked` 和 `out_of_scope`。`blocked` 表示当前缺少足以作出结论的证据，应返回 `Inconclusive`，而不是默认通过。

## 11. 四类设计缺陷

### 11.1 代理指标失效

指标提高不一定代表构念提高。引用数可通过堆砌无关来源提高，自动化率可通过不当减少升级提高，风险召回可通过把所有条款标成风险提高。代理指标适合诊断；只有经过验证并与互补证据组合后，才能支持有限门禁。

### 11.2 评测对象漂移

逐项核对：决策对象、Charter Target、实际运行对象、证据对象和报告结论对象。身份、权限、检索或工具链任一被绕过，都会改变结论含义。

### 11.3 场景遗漏

按真实流量抽样能够估计一般表现，却可能漏掉低频高风险事件。应同时覆盖信息缺失、规则冲突、版本边界、工具超时、并发重复、身份差异和攻击场景。

### 11.4 不可验证需求

“零幻觉”“绝对安全”“像专家一样”是价值愿景，不是有限测试可证明的命题。应分解为有限范围内的可回答性、有据性、权限隔离、关键风险召回、适当拒答和人工升级。如果关键状态不可观察，应先建设观测和治理能力。

## 12. 决策结果必须允许证据不足

| 结果 | 含义 | 动作 |
|---|---|---|
| Pass | 声明范围内证据充分且门禁满足 | 批准既定范围并进入监控 |
| Fail | 确认违反关键门禁或不可接受退化 | 阻断、修复并回归 |
| Inconclusive | 证据质量、覆盖或不确定性不足 | 保持原权限并补证 |
| Conditional Pass | 仅部分身份、领域或权限有充分证据 | 只开放被证明的子范围 |
| Exception | 责任人显式接受有期限的残余风险 | 记录理由、补偿控制和到期复审 |

Conditional Pass 不能掩盖关键风险失败；它只适用于能够明确隔离且证据充分的子范围。

## 13. 三个端到端案例

### 13.1 退款 Agent

从“退款答复正确”扩展到工具权限、审批、幂等、超时和支付账本最终状态。详见 [完整案例](examples/refund-agent/evaluation-case.yaml)。

### 13.2 合同审查 Agent

以高严重性风险召回、原文 span、严重性解释、专家分歧和人工责任边界为证据。详见 [完整案例](examples/contract-agent/evaluation-case.yaml)。

### 13.3 企业知识助手

把可回答性、主张有据性、文档新鲜度、ACL 全路径与正式流程边界连接到条件批准。详见 [完整案例](examples/knowledge-assistant/evaluation-case.yaml)。

## 15. 可执行实验：Requirements-to-evidence review

本实验评审设计产物，不声称已经运行真实 Harness 或获得生产结论。

1. 选择一个明确的候选决定，复制并填写 [Evaluation Charter](evaluation-charter.yaml)。
2. 用 [Stakeholder Impact Map](stakeholder-impact-map.yaml) 补齐直接用户、数据主体、资产负责人和治理角色，至少形成一条端到端影响链。
3. 依据 [Risk Taxonomy](risk-taxonomy.yaml) 写出关键风险陈述，标记不可补偿风险和失败动作。
4. 为每项关键风险填写 [Construct Definition](construct-definition.yaml)，给出正例、反例、边界例和不能推出的结论。
5. 在 Charter 中写出评测问题，再用 [Evidence Requirements](evidence-requirements.yaml) 声明来源、场景矩阵、参考标准、观察、评分与充分性。
6. 填写 [Requirements Traceability](requirements-traceability.yaml)，做两遍审查：从需求向前检查是否落到动作；从每项证据和指标反向检查其决策用途。
7. 将每条链标记为 `covered`、`partial`、`blocked` 或 `out_of_scope`；关键链为 `blocked` 时，预期结论必须是 `Inconclusive`。

实验交付标准：所有关键风险均可追踪到构念、问题、证据、门禁和责任人；没有孤立指标；范围与实际 Target 一致；不可验证愿景已被操作化或明确保留为限制。

## 16. 结果分析示例

| 观察结果 | 合理结论 | 不合理推断 |
|---|---|---|
| 声明范围证据充分，所有关键硬门禁满足 | `Pass`，只批准该范围 | 系统在所有未来场景绝对安全 |
| 确认一次未授权信息进入普通员工上下文 | `Fail`，阻断相关知识域 | 最终回答未展示信息，所以可通过 |
| 文档缺少生效、废止和替代关系 | `Inconclusive`，先补知识治理 | FAQ 正确率高，所以当前制度可靠 |
| HR 通用制度证据充分，IT 无答案覆盖不足且两域可隔离 | `Conditional Pass`，只开放 HR 通用制度 | 用条件通过掩盖不可隔离的关键失败 |

结果分析必须同时说明支持什么、不能支持什么、残余风险、适用时间以及重新评测触发条件。

## 17. 单元测评与参考答案

1. **十万条文档生成问答能否证明知识助手覆盖真实场景？** 不能。规模不等于代表性，它通常过度覆盖有答案、措辞接近文档的场景，并遗漏权限、冲突、过期和无答案问题。
2. **引用率达到 100% 能否证明有据性？** 不能。还需验证关键原子主张是否被引用 span 蕴含、引用是否完整、当前有效且对用户授权。
3. **基础模型政策问答优秀，能否批准退款 Agent 自动执行？** 不能。决策对象是包括政策、工具、审批、重试和账本状态在内的完整行动链路。
4. **高严重性风险召回率越高是否一定越好？** 不一定。把所有条款都标为风险可以提高召回却摧毁律师可用性；必须同时报告关键类别漏检、候选负担、原文定位和严重性依据。
5. **要求“零幻觉”应当删除吗？** 不应删除其价值目标；应分解为可回答性、有据性、新鲜度、适当拒答等可验证构念，并承认有限证据不能证明开放世界零风险。
6. **关键状态无法观察时应判 Fail 还是 Pass？** 通常是 `Inconclusive`。先建设观测、参考标准或环境状态证据；不能用容易测的文本代理冒充。
7. **什么时候可以 Conditional Pass？** 只有证据充分的子范围能够明确隔离，且被排除范围不会绕过控制时；关键风险已经失败时不能使用。
8. **指标没有对应风险或决定，但有调试价值怎么办？** 可保留为诊断指标，明确它不参与门禁；若没有任何使用者或动作则删除。

## 18. 延伸阅读

- A1.1 的 Evaluation Target、Risk Definition 与 Gate Policy：用于把本单元产出的需求链继续落实为实验和门禁。

## 19. 单元结论

可以用一句话审查任何评测方案：

> 这份证据究竟证明了哪个版本的什么系统，在什么人、什么场景、什么权限和什么控制条件下，可以支持哪个具体决定；它又明确不能证明什么？

无法回答这句话的方案，即使拥有大规模数据、复杂 Judge 和漂亮仪表盘，也没有形成可靠的评测设计。
