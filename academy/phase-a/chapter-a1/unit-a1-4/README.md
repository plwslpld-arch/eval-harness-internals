# A1.4｜从评测问题到任务与场景

> 本单元把已经定义好的评测问题转换为可执行、可变体化、可覆盖审查的任务与场景。核心不是“多写几道题”，而是让风险、状态、时间、故障和行为约束进入任务设计，使每次运行都能产生与决策相关的证据。

## 1. 学习目标

完成本单元后，应当能够：

1. 解释 Evaluation Question、Scenario Space、Task Spec、Test Case、Variant 和 Trajectory Contract 的关系。
2. 从风险触发条件和失败机制反推场景轴，而不是只按历史流量出题。
3. 编写包含前置状态、输入、允许动作、成功条件和证据需求的 Task Spec。
4. 设计受控变量、反事实对、预期不变关系和变形关系。
5. 将多轮交互、时间边界、工具故障、重试和并发写入场景。
6. 使用 Coverage Matrix 发现空白、过度聚集和不可执行组合。
7. 通过质量门判断 Task Spec 是否有资格进入后续数据、评分与 Harness 工程。

## 2. 术语链：从问题到一次运行

```text
Evaluation Question
→ Scenario Space
→ Task Spec
→ Test Case
→ Variant / Metamorphic Family
→ Trial in Environment
→ Observation
→ Score and Decision Evidence
```

- **Evaluation Question** 规定想回答的构念与决策用途。
- **Scenario Space** 定义目标世界中会改变风险或期望行为的轴和组合。
- **Task Spec** 定义一类可执行任务的接口、前置状态、约束和成功语义。
- **Test Case** 把 Task Spec 实例化为具体输入、状态、期望和证据引用。
- **Variant Plan** 对同一语义构造受控、反事实、不变或变形样本族。
- **Trajectory Contract** 约束 Agent 在完成任务过程中允许和禁止的行为。
- **Coverage Matrix** 记录重要场景是否被任务和样本实际覆盖。

Task Spec 不是提示词，Test Case 也不只是问题文本。对于 Agent，一次任务还包括环境初态、可用工具、权限、时间、故障、允许轨迹和最终状态。

## 3. 风险驱动的 Scenario Space

从风险陈述中的触发条件、失败机制、受影响方和控制反推场景轴：

| 场景轴 | 示例取值 | 为什么重要 |
|---|---|---|
| 用户与权限 | 普通用户、经理、审核员、失效身份 | 决定可见信息与允许动作 |
| 输入完整性 | 完整、缺失、矛盾、污染 | 触发猜测、拒答或升级 |
| 规则与边界 | 常规、阈值前后、例外、规则冲突 | 暴露边界判断和优先级问题 |
| 环境状态 | 初始、处理中、已完成、状态未知 | 决定动作是否合法和幂等 |
| 时间 | 生效前后、到期前后、时区、延迟 | 影响政策、资格和重试 |
| 依赖 | 正常、超时、拒绝、部分失败、脏返回 | 检验停止、恢复和升级 |
| 交互 | 单轮、多轮澄清、更正、上下文切换 | 检验状态保持与信息更新 |
| 并发 | 重复提交、交叉请求、乱序回调 | 暴露重复副作用和竞态 |
| 对抗 | 越权诱导、提示注入、伪造证据 | 检验控制是否真正生效 |

场景空间不是所有轴的笛卡尔积。应优先覆盖高严重性风险、交互强的组合、决策边界和历史事故，再用流量代表性估计一般表现。

## 4. Task Spec 的最小合同

一份可执行 Task Spec 至少包括：

1. **Purpose 与 traceability**：它回答哪个评测问题、控制什么风险和构念。
2. **Actors 与 authority**：谁发起任务，身份和权限是什么。
3. **Preconditions**：业务实体、文档、会话、时钟和依赖的初始状态。
4. **Input contract**：用户输入、附件、上下文和允许的变化。
5. **Available actions**：可用工具、参数边界和副作用。
6. **Success semantics**：期望结果、最终状态、必须发生和不得发生的行为。
7. **Stop 与 escalation**：什么时候拒答、停止、澄清或交给人工。
8. **Observations**：需要记录的答案、轨迹、工具、状态和时间。
9. **Budgets**：轮数、步骤、时间、调用和成本上限。
10. **Reset 与 replay**：如何恢复初态、隔离运行并重放失败。

成功条件必须可观察。“表现专业”“合理处理”不是成功语义；“高严重性风险候选包含原文 span，附件缺失时创建律师复核标志”才是。

## 5. Test Case：把规格实例化

Test Case 必须引用一个 Task Spec，并给出确定的 case ID、场景坐标、输入夹具、前置状态、期望、禁止行为和证据捕获。它回答的是“这一次具体运行什么”，而不是重新发明任务语义。

同一 Task Spec 可以实例化：

- 流量代表性样本，用于估计常规总体；
- 风险定向样本，用于测试低频高伤害失败；
- 边界样本，用于阈值前后和规则优先级；
- 回归样本，用于固定历史事故；
- 对抗样本，用于验证权限与输入控制。

这些样本的抽样含义不同，报告时不能把风险定向集当作真实流量发生率。

## 6. 受控变量、反事实、不变与变形关系

### 6.1 受控变量

一次只改变一个有解释力的因素，例如金额从上限下方变到上方，保持订单、用户、政策和工具状态不变。这样才能把行为差异归因给目标变量。

### 6.2 反事实对

构造仅在敏感或决策变量上不同的成对样本。例如相同合同只改变责任上限条款；相同知识问题只改变用户角色。反事实关系应事先声明预期变化。

### 6.3 不变关系

输入发生不应改变语义的变化时，关键结果应保持一致。例如改写措辞、调整无关段落顺序、替换非敏感姓名，不应改变政策资格或风险类别。

### 6.4 变形关系

当输入按已知规则变化时，输出应按可预测关系变化。例如退款金额跨越自动上限后，结果应从执行切换为升级；撤销授权后，检索结果和回答都不得包含受限信息。

这些关系能在没有单一完整参考答案时提供结构化检查，但关系本身也需领域确认。

## 7. 多轮、状态、时间、故障与并发

Agent 场景必须描述事件序列，而不只是静态输入：

```text
初始状态
→ 用户请求
→ Agent 读取与决策
→ 工具调用或澄清
→ 环境返回或故障
→ 重试、停止或升级
→ 最终回答与最终状态
```

- **多轮**：后续更正是否覆盖旧信息；上下文切换后是否错误沿用权限或实体。
- **状态**：任务开始时是否已经完成、处理中或未知；最终文本是否与真实状态一致。
- **时间**：政策生效、合同期限、退款窗口和文档版本边界。
- **故障**：超时不等于失败；未知结果不能被当成未执行；部分失败需要补偿或升级。
- **并发**：重复请求、并行会话和乱序回调需要业务键、幂等和最终状态断言。

## 8. Trajectory Contract

结果正确并不保证路径安全。Trajectory Contract 定义：

- 允许和禁止的工具及调用顺序；
- 调用前必须满足的授权、证据和状态条件；
- 最大调用次数、重试策略和幂等要求；
- 哪些观察必须先发生，哪些写操作不得发生；
- 何时必须澄清、拒答、停止或升级；
- 最终回答必须与环境最终状态一致。

合同应描述外部可验证行为，不要求披露或评分模型内部思维过程。

## 9. Coverage Matrix

Coverage Matrix 把风险、场景轴、Task Spec、Test Case 和状态连接起来。至少报告：

- 每项关键风险是否有正向、负向、边界、故障和恢复场景；
- 每个重要身份、领域、语言、时间与权限切片是否覆盖；
- 每个硬门禁是否有能触发失败条件的样本；
- 组合覆盖是 planned、implemented、executed 还是 blocked；
- 空白是有意排除、证据阻塞还是遗漏；
- 哪些格子属于流量代表性，哪些属于风险定向，不混用分母。

覆盖数量不是充分性的证明。十个同质样本不能替代一个关键边界场景。

## 10. 三个端到端案例

### 10.1 退款 Agent

围绕金额与政策边界、订单状态、审批、工具超时、未知结果、重试和并发，约束账本副作用与人工升级。详见 [完整案例](examples/refund-agent/evaluation-case.yaml)。

### 10.2 合同审查 Agent

围绕合同类型、风险类别、显式或跨条款表达、附件缺失、OCR 故障与专家分歧，约束原文定位和律师责任边界。详见 [完整案例](examples/contract-agent/evaluation-case.yaml)。

### 10.3 企业知识助手

围绕身份、ACL、可回答性、文档版本、来源冲突、提示注入和正式流程请求，约束检索、回答、引用和拒答。详见 [完整案例](examples/knowledge-assistant/evaluation-case.yaml)。

## 11. Task Spec 质量门

进入后续工程前逐项审查：

- [ ] 每个任务引用明确的评测问题、风险和构念。
- [ ] 前置状态和运行时变量足以重建场景。
- [ ] 成功、失败、停止和升级条件可观察。
- [ ] 工具、权限、副作用、预算和最终状态有合同。
- [ ] 受控变量和变体关系具有因果解释。
- [ ] 高风险低频、边界、故障、多轮与并发得到定向覆盖。
- [ ] 场景矩阵不存在未解释的关键空白。
- [ ] 样本用途与分母不混淆。
- [ ] 不依赖未设计的 Scorer 或尚不存在的观察能力来定义“成功”。
- [ ] 任务没有超出 Evaluation Question 和 Claim Boundary。

任一关键项缺失时，Task Spec 状态应为 `blocked`，不能直接交给数据生成或自动执行。

## 12. 可执行实验：Question-to-task review

本实验设计任务资产，不声称已运行真实 Harness。

1. 选择一个 A1.2 Evaluation Question，复制 [Scenario Space](scenario-space.yaml) 并从风险触发条件生成场景轴。
2. 选择一个关键场景，填写 [Task Spec](task-spec.yaml)，明确前置状态、输入、动作、成功和停止语义。
3. 用 [Test Case](test-case.yaml) 实例化一个常规案例和一个高风险边界案例。
4. 用 [Variant Plan](variant-plan.yaml) 构造至少一组反事实对、一项不变关系和一项变形关系。
5. 对 Agent 填写 [Trajectory Contract](trajectory-contract.yaml)，约束工具顺序、副作用、重试和升级。
6. 更新 [Coverage Matrix](coverage-matrix.yaml)，标记 planned、implemented、executed、blocked 或 excluded。
7. 运行 Task Spec 质量门；关键项 blocked 时停止进入数据、Scorer 或 Harness 实现。

实验交付标准：评测问题能追踪到场景、任务、案例、变体和轨迹；每项期望均可观察；覆盖空白有明确理由与动作。

## 13. 结果分析

| 发现 | 解释 | 动作 |
|---|---|---|
| 常规流量覆盖充分，但关键超时场景为空 | 一般表现可估计，状态安全问题不可回答 | 结论 `Inconclusive`，补故障任务 |
| 反事实对只改变角色，输出却泄露相同受限内容 | 权限变量未改变行为 | 关键风险 `Fail`，阻断相关范围 |
| 同义改写导致结论波动，但关键事实与状态不变 | 不变关系失败，存在表述敏感性 | 扩展变体族并定位路由或模型问题 |
| 金额跨阈值后从执行切换为升级 | 变形关系满足 | 作为边界证据，不推广到其他政策 |
| 高风险格子 planned 但未 executed | 计划不等于证据 | 不得在报告中写成已覆盖 |

## 14. 单元测评与参考答案

1. **Scenario Space 是否应穷举所有轴组合？** 不应。使用风险、交互强度、边界和流量权重选择重要组合，并记录排除理由。
2. **Task Spec 与提示词有什么区别？** Task Spec 是评测任务合同，包含状态、动作、成功和观察；提示词只是系统实现输入之一。
3. **最终答案正确，Trajectory Contract 失败，任务算通过吗？** 对有过程安全要求的 Agent 不算。危险副作用不能被文本正确补偿。
4. **风险定向集的失败率能代表生产发生率吗？** 不能。它是刻意富集风险的集合，主要用于发现和门禁，而不是估计自然流量比例。
5. **反事实样本可以同时改用户角色和问题措辞吗？** 不宜。若要归因角色影响，应保持其他关键因素不变。
6. **没有标准答案时能否使用变形关系？** 可以，但关系和预期变化必须经领域确认，且不能替代所有直接证据。
7. **超时后重试成功是否一定通过？** 不一定。先前调用可能已产生未知副作用，必须检查幂等键和最终状态。
8. **Coverage Matrix 中 implemented 是否等于 covered？** 不等于。只有执行成功、证据有效且满足预定覆盖语义后，才能声称已覆盖。

## 16. 范围与延伸阅读

本单元明确不展开：数据采集、清洗、标注与版本治理；Scorer、rubric、Judge 校准和统计聚合；Harness、工具模拟器、隔离和执行引擎实现。这些工作以本单元的任务合同为输入，在后续单元分别展开。

延伸阅读：A1.2 的 Requirements-to-evidence 追踪；A1.3 的 Target 与 Runtime State；组合测试与 pairwise testing；property-based testing；metamorphic testing；状态机测试与并发线性化。使用外部方法时应结合目标系统风险，而不是机械追求组合数量。

## 17. 单元结论

高质量任务设计需要回答：

> 哪项风险在什么场景和初始状态下被触发，Agent 可以采取什么路径，哪些行为必须或不得发生，什么最终状态构成成功，以及这些案例共同覆盖了评测问题的哪一部分？

没有场景空间的题库容易遗漏风险；没有 Task Spec 的样本无法稳定执行；没有轨迹合同的 Agent 评测会把危险过程隐藏在正确答案后；没有覆盖矩阵的“很多测试”无法说明证据缺口。
