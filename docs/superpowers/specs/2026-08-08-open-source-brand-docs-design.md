# Evalorium 开源品牌与文档体系设计

- 状态：已批准，待实施
- 日期：2026-08-08
- 适用仓库：`plwslpld-arch/evalorium`
- 设计范围：开源项目入口、长期文档体系、能力达成证据、跨设备 Handoff、品牌与 Logo 资产

## 1. 背景

Evalorium 当前已经是公开的 Apache-2.0 仓库，但仓库内容仍是最小学习骨架。现有 README 只能说明基本定位，尚不足以承担以下职责：

1. 向首次访问者清楚解释 Evalorium 是什么、为什么存在以及与普通评测库的区别。
2. 准确展示 Academy 与 Platform 的关系。
3. 展示完整目标范围，同时区分愿景、在建能力和已交付能力。
4. 将原始企业 AI 质量岗位要求映射到知识、实践和证据。
5. 支持跨电脑、跨会话、跨贡献者恢复上下文。
6. 提供一致、可维护、适合开源传播的品牌身份。

本设计建立一套可以伴随 Evalorium 从学习项目发展为生产级平台的文档和品牌基础。

## 2. 设计原则

### 2.1 证据优先

仓库不得用目标代替成果。所有能力必须明确标注为以下状态之一：

- `planned`：已经确定目标，但尚未进入实现。
- `learning`：正在学习、实验或形成设计。
- `implemented`：已有可运行实现和基础验证。
- `validated`：已有可复现实验、测试、基准或用户证据。
- `production-proven`：已有真实生产采用和业务结果。

任何 JD 覆盖、能力水平和成熟度声明都必须链接到可检查的证据。

### 2.2 README 负责导航，深度文档负责解释

README 应让访问者在数分钟内理解项目，而不是承载全部细节。架构、路线图、成熟度、能力标准和治理分别进入独立文档。

### 2.3 学习与产品共同交付

Academy 不是临时笔记目录，而是 Evalorium 的正式组成部分。每个知识单元应形成教材、实验、测评和工程证据；Platform 则将这些方法实现为可运行系统。

### 2.4 跨设备状态以 Git 为准

对话是交互界面，仓库是持久事实来源。任何新会话只读取规定入口文件，就应能够恢复当前状态和准确下一步。

### 2.5 品牌资产必须可维护

生成式图像只用于探索方向。正式 Logo 以手工整理的 SVG 为源文件，并由 SVG 派生 PNG。Logo 必须支持浅色、深色、单色和小尺寸使用场景。

## 3. 方案比较

### 方案 A：单一超长 README

优点是入口集中、初始成本低；缺点是内容很快失控，双语维护困难，进度与愿景容易混淆，不适合长期平台项目。

### 方案 B：双语 README 与分层专业文档

README 负责产品叙事和导航，专业文档分别维护愿景、范围、架构、路线图、成熟度、能力标准和品牌规范。该方案具有清晰边界，适合持续演进和社区协作。

### 方案 C：优先建设完整文档网站

展示能力最好，但当前产品与课程尚未形成稳定结构。此时建设网站会过早固化信息架构，并增加不必要的前端维护成本。

采用方案 B。GitHub Pages 保留在路线图中，待课程 HTML 和平台文档形成稳定内容后建设。

## 4. 信息架构

### 4.1 仓库根目录

| 文件 | 作用 |
|---|---|
| `README.md` | 英文主入口，包含中文入口 |
| `README.zh-CN.md` | 完整中文入口，与英文版结构一致 |
| `START_HERE.md` | 跨设备和新会话恢复入口 |
| `CONTRIBUTING.md` | 贡献方式、开发流程和证据要求 |
| `SECURITY.md` | 漏洞报告和敏感信息政策 |
| `CODE_OF_CONDUCT.md` | 社区行为准则 |
| `LICENSE` | Apache-2.0 许可证 |
| `.editorconfig` | 编辑器基础格式约束 |
| `.gitattributes` | UTF-8/LF 和文本文件行为约束 |
| `.gitignore` | 本地状态、临时设计稿和敏感信息忽略规则 |

### 4.2 `docs/`

| 文件 | 作用 |
|---|---|
| `docs/README.md` | 文档索引 |
| `docs/VISION.md` | 愿景、用户、问题和价值主张 |
| `docs/SCOPE.md` | 完整范围、边界和非目标 |
| `docs/ARCHITECTURE.md` | 目标架构、模块职责和数据流 |
| `docs/ROADMAP.md` | 阶段目标、退出条件和交付物 |
| `docs/PROJECT_MATURITY.md` | 项目成熟度等级和当前状态 |
| `docs/MASTERY_STANDARD.md` | “掌握”和“专精”的可验证定义 |
| `docs/JD_COMPETENCY_MAP.md` | 岗位要求到学习、项目与证据的映射 |
| `docs/BRAND.md` | Logo、颜色、留白、最小尺寸和错误用法 |

### 4.3 `docs/assets/brand/`

正式品牌资产包括：

- `evalorium-logo.svg`：浅色背景主横版。
- `evalorium-logo-dark.svg`：深色背景横版。
- `evalorium-mark.svg`：仅图形标志。
- `evalorium-mark-mono.svg`：单色标志。
- `evalorium-logo.png`：README 和不支持 SVG 的场景。
- `evalorium-mark-512.png`：社交头像和仓库图标。
- `source-concept.png`：生成式探索稿，仅用于设计溯源，不作为正式源文件。

### 4.4 `handoffs/`

- `handoffs/CURRENT.md`：当前唯一有效 Handoff。
- `handoffs/TEMPLATE.md`：统一 Handoff 模板。
- `handoffs/archive/`：历史 Handoff，文件名包含日期和主题。

Handoff 必须包含：

1. 已确认决策。
2. 当前状态和完成证据。
3. 本次变更。
4. 精确下一步。
5. 未解决问题和风险。
6. 验证命令与结果。
7. 最近提交和远程状态。

### 4.5 `progress/`

`progress/state.yaml` 是机器可读的当前学习状态，`progress/PROGRESS.md` 是对应的人类可读视图，`progress/competency-matrix.md` 记录证据支持的能力状态。

三者必须在每次正式学习结束时同步更新。发生冲突时，以最近一次经过验证并提交的 `state.yaml` 为起点，通过 Handoff 和 Git 历史恢复，而不是静默覆盖。

## 5. README 设计

英文和中文 README 采用相同结构：

1. Logo、项目名称和一句话定位。
2. 明确的当前阶段提示，避免给人“平台已经完成”的错误印象。
3. Why Evalorium：现有工具碎片化与企业发布决策之间的缺口。
4. 核心原则：Evidence before release、uncertainty-aware、reproducible、risk-driven。
5. Academy 与 Platform 双轨关系。
6. 目标产品架构和模块地图。
7. Agent Environment Harness 的定位。
8. Eval-to-RL 闭环。
9. 项目成熟度与已交付内容。
10. 学习路线和跨设备恢复入口。
11. 路线图、贡献、安全和许可证入口。

README 不添加虚假的下载量、测试、覆盖率或生产采用徽章。只有自动化流程真实存在后，才增加对应状态徽章。

## 6. 能力达成与 JD 映射

`MASTERY_STANDARD.md` 将能力分为五级：

1. 理解：能够解释概念、假设和适用边界。
2. 应用：能够在有边界的任务中正确使用方法。
3. 设计：能够从零设计体系并说明权衡。
4. 验证：能够用统计、实验和失败分析证明有效性。
5. 引领：能够在真实团队和业务中推动采用、治理和持续改进。

“完成课程”最多证明理解和部分应用；“完成可运行项目并通过验证”才能证明设计与验证；“真实组织采用和业务结果”才支持引领层级。

`JD_COMPETENCY_MAP.md` 对原始岗位的每项要求记录：

- JD 原始能力。
- 必修知识单元。
- 对应实验或 Capstone。
- Evalorium 平台交付物。
- 验证方式。
- 当前状态。
- 尚不能由开源项目替代的真实经历要求。

该文件用于学习规划和证据管理，不作招聘结果保证。

## 7. Logo 设计

### 7.1 品牌概念

正式方向命名为 **Evidence Gate**。

- 外部方形：受控评测环境和稳定边界。
- 三条负空间通道：能力、可靠性和安全等多维证据。
- 汇聚结构：不同信号经过校准形成一致判断。
- 中央门：发布决策和质量门禁。
- 隐含字母 E：建立与 Evalorium 名称的识别关系。

### 7.2 视觉风格

- 精确、安静、可信，接近科学仪器和现代开发者平台。
- 扁平二维几何，不使用透视、阴影、装饰性渐变或细碎节点。
- 主色为 Midnight Navy `#0B1020`。
- 强调色为 Electric Iris `#6C63FF`。
- Signal Mint `#2DD4BF` 仅保留为产品数据视觉的辅助色，不进入主 Logo。
- 字标采用系统可替代的现代无衬线风格；SVG 中不依赖远程字体。

### 7.3 可用性约束

- 图形标志必须在 16px 下保持主要轮廓。
- 必须存在纯单色版本。
- SVG 不包含外部资源、脚本、位图嵌入或字体网络依赖。
- 横版和图形版必须具有明确的安全留白。
- PNG 必须从批准的 SVG 派生，不反向临摹生成图。

## 8. 数据与工作流

### 8.1 学习会话开始

1. `git pull --rebase`。
2. 读取 `START_HERE.md`。
3. 读取 `progress/state.yaml`、`PROGRESS.md` 和 `handoffs/CURRENT.md`。
4. 从 `next_actions` 恢复。

### 8.2 学习会话结束

1. 更新课程成果和实验。
2. 更新机器可读状态和人类可读进度。
3. 更新能力证据。
4. 归档旧 Handoff 并生成新 Handoff。
5. 运行格式、链接、敏感信息和内容一致性检查。
6. 提交并推送。

### 8.3 文档成熟度更新

只有当证据文件、验证命令和对应提交均存在时，能力状态才能升级。删除或失效的证据必须触发状态降级或风险说明。

## 9. 失败处理

- README 与详细文档冲突：以专业文档为准，并在同一提交中修正 README 摘要。
- `state.yaml` 与 `PROGRESS.md` 冲突：停止推进下一单元，通过 Git 历史和 Handoff 修复。
- 链接失效：验证失败，禁止把文档升级标记为完成。
- SVG 无法解析或 PNG 与 SVG 不一致：品牌交付不通过。
- 检测到疑似密钥：停止提交，撤销泄露凭据并清理历史风险。
- 文档声称的成熟度缺少证据：将状态降为可证明的等级。

## 10. 验证策略

实施完成后至少执行：

1. `git diff --check`，检查空白和补丁问题。
2. Markdown 内部链接检查。
3. YAML 解析和必要字段校验。
4. SVG XML 解析、安全属性和尺寸检查。
5. PNG 文件存在性、格式和尺寸检查。
6. UTF-8 解码检查。
7. 敏感信息模式扫描。
8. README 中所有状态声明与实际文件逐项对照。
9. GitHub 远程提交与本地提交一致性检查。

## 11. 实施顺序

1. 建立编码、忽略和基础社区文件。
2. 完成 Logo SVG 源文件及派生资产。
3. 完成英文与中文 README。
4. 完成愿景、范围、架构和路线图。
5. 完成成熟度、能力标准和 JD 映射。
6. 完善 START_HERE、Handoff 和 progress 协议。
7. 增加验证脚本或工作流。
8. 本地验证、远程验证和 GitHub 展示检查。

## 12. 验收标准

本设计只有在以下条件全部满足时才算实施完成：

- GitHub 仓库保持公开并使用 Apache-2.0。
- 中英文访问者都能从 README 理解产品定位、当前状态和导航。
- 目标范围完整覆盖原始企业 AI 质量岗位涉及的知识与实践。
- 所有“达到水平”的表述均有清晰等级、证据和限制说明。
- 任意新电脑能够仅依靠仓库恢复学习进度。
- Logo 具有主版、深色版、图形版、单色版和 PNG。
- 文档不存在占位符、断链、编码错误或敏感信息。
- 本地与远程主分支提交一致，工作区干净。

## 13. 非目标

本次工作不实现 Evalorium Platform 的运行时代码，不建设完整 GitHub Pages 网站，不声称已经达到生产级成熟度，也不把开源项目包装成不存在的企业采用经历。
